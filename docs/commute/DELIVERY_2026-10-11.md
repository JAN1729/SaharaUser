# Sahara passenger MVP delivery

This delivery uses the approved minimalist chat design, the central computer server, scraped public transport pages and the existing driver project. It does not create another driver app or driver backend. This is a debug pilot build; the feature and data boundaries below are part of the delivery.

## What is implemented

| Feature | Passenger behavior | Backend behavior and limits |
|---|---|---|
| Chat planning | Enter places, date and preferences; refine the same conversation | OpenRouter/DeepSeek extracts a constrained request. Deterministic validation and planning decide the journey; the language model cannot invent inventory |
| Multimodal options | Compare complete journeys, fares, duration and connections | Connects rail, scraped KSRTC bus and scraped flight offers with known terminal access/transfer/egress links. Other mode types require an actual configured feed |
| Price comparison | Shows total fare or clearly labels an incomplete total | Calculates minor currency units, per-person versus party fares and transfer costs. Unknown fares stay unknown |
| Constraints | Ask for a budget, fewer transfers, less walking, a deadline or wheelchair access | Preserves numerical limits; comfort favors fewer transfers/known walking and feasible journeys. Unknown accessibility/amenities are disclosed |
| Source collection | Progress and partial results appear while sources finish | Bounded concurrent public HTML/rendered DOM collectors, cache, route/date checks, evidence timestamps, challenge/timeout reporting. No public transport inventory APIs |
| Kerala and intercity | Search mapped Kerala terminals and supported intercity destinations | No Kerala-only geographic restriction. The current 22 terminal mappings cover selected cities, not every stop or all India services |
| Flights | Flight results participate in the same comparison when a dated quote is available | Google Flights public rendered cards, INR/date/route/fare validation, bounded query dates; no flight inventory API. Quotes are neither guaranteed seats nor bookings |
| Journey following | Follow the selected route, refresh or stop; confirm boarding/completing a leg | Owner-bound saved progress and guidance, 10-second foreground guidance checks and 90-second source revalidation. No automatic boarding assumption |
| Boarding guidance | Shows terminal, departure and instructions with precision label | Seed terminals are approximate. Exact boarding instructions require verified source details |
| Connection checks | Shows margin or a connection risk, and whether timing is verified | Includes transfer travel, processing and safety buffer. A timetable alone cannot become verified live arrival |
| Recovery | Refreshed alternatives can be selected and mapped | Replans from confirmed progress/current time, preserving an explicit deadline and already-started fare identity. If no verified alternative exists, none is invented |
| Existing driver connection | Nearby participating vehicle GPS can appear in text and on the map | Read-only adapter to the supplied Supabase vehicles/route_stops/locations schema. Only active registered vehicles, fresh started trips and usable GPS accuracy; never reads unrelated location rows when fleet is empty |
| Fleet evidence | Nearby GPS is distinct from a confirmed service on the itinerary | No fares, seats, ETA or approaching claims are invented from raw coordinates. Journey matching requires an explicit vehicle ID; verified ETA evidence is separately required |
| OpenStreetMap | Terminal pins, source route shapes when installed, selected route, fit control, zoom/pan, attribution and offline hint | Validates geometry and uses a directed local graph with mode/service filtering. Missing service geometry produces pins and a notice, not a straight line presented as a road/rail route |
| Central computer | Kotlin acts as the interface; server stores searches and journeys | FastAPI plus SQLite owner-bound records, incremental stream, retained immutable journey snapshots, interrupted-search recovery, local access checks and bounded request limits |
| Credentials | Server settings use a masked gateway key | OpenRouter stays server-side in ignored Windows-protected storage. Existing driver connection is protected locally; provider secrets are not built into the passenger APK |

## Travel status behavior

Tap **Follow this journey** on a selected option. The companion shows the boarding terminal, timetable departure, connection margin, source warnings and any participating nearby fleet. Tap **I've boarded this leg** only after boarding; tap **I've completed this leg** after finishing it. Confirmations must follow the itinerary in order and cannot move saved progress backward. A confirmation for a service that has not departed is rejected. Invalid saved travel status can be explicitly repaired; valid progress cannot be reset through that repair action.

Polling belongs to the selected route and active screen above the scrollable conversation, so scrolling does not stop a followed journey. It pauses in the background and stops on navigation, a new search, route change, conversation clear or Stop following. Unknown transport outcomes preserve the pending confirmation for reconciliation; definite rejected confirmations require explicit reconfirmation. GPS markers expire even when a source refresh is slow. Replanning offers choices without purchasing tickets or claiming a protected connection.

## Remaining real-data and release gates

- **Coverage:** selected terminal mappings and checked source pages, not all Kerala neighborhoods or nationwide inventory. Train/bus/flight pages can time out, change markup or challenge automated access. Source failures remain visible. Adding verified provider mappings expands coverage without a region lock.
- **Map geometry:** no real service route graph is installed. The built app shows real OSM tiles and approximate terminal pins for those legs. Verified service shapes/boarding locations must be supplied before claiming accurate full route polylines.
- **Operator network:** no registered fleet is currently available. Exact boarding points, reliable approaching/arrival estimates, private-bus/auto fares and bookable local schedules need participating operator data. Raw GPS alone is insufficient.
- **Traffic, metro, ferry and local services:** no verified live traffic feed or broad inventory source for these modes is connected. Supporting their mode types is not proof of coverage.
- **Notifications:** foreground companion is implemented. The separate backend watch worker can record refreshed events; guaranteed Android background alerts/push are not enabled.
- **Production:** account authentication, hardened existing fleet policies, authenticated HTTPS hosting, deployment, physical-phone/LAN validation and Play release checks remain separate. Android lint had dependency-download failures and is not claimed passing.

These gates cannot be solved by inventing data or silently showing demo services in Live mode. The delivered code exposes the gaps and remains usable for verified source coverage and explicit demo exploration.
