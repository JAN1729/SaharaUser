# Jev mobility intelligence in Sahara

The Python server now uses Jev through OpenRouter's Decisions API. The current protected OpenRouter key is reused; no TypeSafe account, new Java application or provider inventory API is required. Kotlin remains the interface and the existing passenger APK stays compatible.

## Implemented behavior

- Transport matching: common abbreviations are normalized in code. Geography, freshness, corridor/direction, operator and explicit identity conflicts, service date/departure and ordered route stops are checked before semantic classification. Ambiguous candidates use one batched Choice/Noul request. Multiple matching candidates remain unresolved. Source records and decisions are retained in owner-scoped SQLite audit records.
- Local-feed integration: a server-owned timetable JSON may supply `stop_records` and `canonical_stops` alongside `legs`. Only a unique verified match can replace an external endpoint ID with an existing terminal ID. Canonical references must agree with the terminal catalogue spatially. Unresolved endpoints are excluded and reported as partial coverage. Known-terminal legs are emitted before alias work; bounded parallel checks only consider stop IDs actually used by the feed. A slow semantic source therefore retains usable partial inventory. Matching never creates a vehicle assignment, fare, seats, GPS observation or map geometry.
- Notice triage: an authenticated source-ingestion caller can submit a dated HTTPS-source notice for an owner-bound journey. Expired/future observations, unrelated scopes and unconfigured source/hostname pairs are filtered in code. Trusted origins must be configured server-side; the default empty registry retains notices for review. Jev classifies kind, relevance and ambiguity together. Strong, explicitly scoped decisions queue investigation; all others retain a review/ignore result. The watch worker uses its existing leases to check pending notices through the deterministic revalidation pipeline. A concurrently stopped watch or changed travel progress suppresses stale events and notice acknowledgements; progress is checked again inside the final database transaction. Retry backoff prevents a pending notice repeatedly forcing a failed/stale refresh. The model decision alone never becomes an arrival claim or a disruption warning.
- Chat routing: narrowly recognized complete route requests and exact budget/preference refinements bypass both AI services. Other messages may be categorized by Jev using closed mobility terms, recognized public terminal IDs, route markers, script and query shape. Arbitrary names, email/phone identifiers, numbers and coordinates are excluded from this classification state. The existing general-purpose extraction receives the original request when needed. Requests about vehicle position, active connections or explanation point to the existing selected-journey controls. Explicit new-route requests cannot be redirected by a mistaken high-confidence follow-up judgment. Rich preferences, relative budgets and accessibility constraints continue through the existing validated extraction/planner path.

Clear tracking/connection phrases also use deterministic routing: “Where is my bus?” directs the passenger to Follow journey without a paid classification or extraction. Explicit relative rupee budgets are calculated in code from a previously validated budget: ₹900 plus “₹200 more” becomes ₹1,100. With no known current budget, Sahara asks for an absolute budget rather than guessing or treating ₹200 as the new total.
- Efficiency and failure behavior: reuse one async HTTP connection pool, four request slots, four-second total decision deadline including queue time, content cache for five minutes, identical-request coalescing, bounded payloads and an outage/rate-limit cooldown. Set `SAHARA_JEV_TIMEOUT_SECONDS` between 0.01 and 10 seconds to override the deadline. Missing keys and outages retain conservative rules/review behavior. Diagnostics report cost, token usage, latency, effective deadline and the last safe failure category (`deadline`, `connection`, `http_status`, or `invalid_response`); no keys or raw provider error bodies are returned.

## Live probe and limits

A real OpenRouter call returned `typesafe/jev-1.13-20260917` for four synthetic independent judgments. Observed call latency was **1,657ms**, cost **USD 0.000025746**, input tokens **613**. The repeated request hit the cache without a second API charge. The judgments classified a stop abbreviation, diversion and connection-check intent. The alias Noul was0.85 even though the relationship Choice selected `same` with confidence1.0; this illustrates why both semantic gates and independent checks are retained.

These examples are synthetic. They establish endpoint compatibility, not real transport matching accuracy or a faster complete journey search. No independent 200–500-record labeled operator dataset is present. Semantic-only matches therefore remain **review-only** by default. The user must obtain actual operator/timetable labels before enabling `SAHARA_JEV_ACCEPT_MATCHES=true`. A classification's confidence is not the probability that a service will arrive or that a notice is true.

The comparison command was also exercised with six explicitly synthetic fixture pairs, only one of which required AI rather than deterministic checks. Rules and the conservative Jev policy each agreed with5/6 fixture labels (one valid-label pair retained for review); the conventional DeepSeek baseline agreed with6/6. The successful Jev semantic call took1,718ms and reportedUSD0.000020118; the conventional arm's slowest pair took988ms and reportedUSD0.00001764. This tiny fixture does **not** show Jev outperforming the baseline. An earlier Jev call exceeded the production two-second deadline and correctly fell back to review. Evaluation uses a separately configurable five-second deadline. Failed/timed-out calls may still be billed without returning usage; diagnostic cost totals include only returned usage.

The initial conventional baseline returned empty text because DeepSeek V4 defaults to high reasoning and exhausted the small output budget. Its optional reasoning was disabled for narrow structured extraction, both in the evaluation baseline and the existing Sahara interpreter; complex conversation remains outside this decision layer. Supported model settings were checked against the official model catalogue and the corrected baseline succeeded.

Jev does not fill missing fleet data, create scrapeable inventory, calculate fares/ETA/transfer margins, provide OSM geometry or enable phone push notifications. The central host and optional watch worker must remain running. No automatic notice crawler or push channel was deployed by this change; ingestion and watch APIs are ready for participating sources.

## Operations and evaluation

The launcher already loads the protected OpenRouter key. Set the following environment variables before starting it if overrides are needed; `.env.example` is documentation and is not automatically loaded:

```powershell
$env:SAHARA_JEV_ENABLED = 'true'
$env:SAHARA_JEV_MODEL = 'typesafe/jev-1.13'
$env:SAHARA_JEV_ACCEPT_MATCHES = 'false'
.\backend\start-central-server.ps1 -ListenAddress 0.0.0.0 -Background
```

The pinned model avoids silent alias changes. `/health` reports the configured decision model and match policy. Authorized `/v1/intelligence/health` reports diagnostics. Configuration health is not a paid model availability test.

Production accepts the `typesafe/jev-1.13` model family only and validates dated response identifiers for that family. The actual responding version is recorded. Moving to a different family requires a code/configuration change and a fresh evaluation, rather than switching to `latest` silently.

`SAHARA_NOTICE_SOURCES` optionally configures exact metadata pairs in the form `source@hostname;source2@hostname2`. It defaults to empty. Unknown pairs stay in review without consuming a model call. An allowlisted URL is not proof that the notice text is true; the source-ingestion job must verify provenance, and the journey verifier must still establish any actionable consequence.

Authenticated interfaces use the existing `Authorization: Bearer <Sahara access key>` and randomly generated `X-Sahara-Session`; keep the latter stable for owner-bound records:

| Endpoint | Purpose |
|---|---|
| `POST /v1/intelligence/reconcile` | `{record: TransportRecord, candidates: [TransportRecord]}`; at most16 candidates |
| `GET /v1/intelligence/reconciliations` | Recent reconciliation audit for that session |
| `POST /v1/journeys/{id}/notices` | Dated notice and explicit terminal/service scope; classification only |
| Existing journey watch/events/guidance endpoints | Run verified refresh and inspect results |

TransportRecord fields: `id`, `source`, `kind` (`stop`, `route`, `service`), `name`, paired `lat`/`lng`, `observed_at`, `expires_at`, and optional `corridor`, `direction`, `operator_id`, paired `identity_namespace`/`identity_id`, ordered `stop_sequence`, `service_date`, `departure`. Identity namespaces must describe the same registry before IDs are compared. Source identity/corridor/coordinate assertions must be verified by ingestion before using them as evidence; a model cannot establish them. Route/service matching requires an identical, nonempty stop sequence; service matching also requires operator/date and either an exact shared identity or comparable departure timestamps.

Notice fields: `text`, `source`, `source_url` (HTTPS metadata; this endpoint does not fetch it), timezone-aware `observed_at`/`expires_at`, and optional `terminal_ids`/`service_ids`. A strong semantic judgment without matched explicit scope remains review-only. Submitting a notice does not itself start an active journey watch.

Run a small paid synthetic probe from `backend` with `OPENROUTER_API_KEY` supplied securely to the server process:

```powershell
python -m scripts.probe_jev
```

For human-labeled evaluation, create JSONL with one independently labeled pair per line:

```json
{"evaluated_at":"2026-10-11T00:00:00+00:00","record":{"...":"TransportRecord fields"},"candidate":{"...":"TransportRecord fields"},"label":"same"}
```

Allowed labels are `same`, `different`, `review`. Use a fixed evaluation time appropriate to the evidence, and do not relabel model outputs as human truth. From `backend`:

```powershell
python -m scripts.evaluate_reconciliation --dataset data/labeled-records.jsonl --engine rules
python -m scripts.evaluate_reconciliation --dataset data/labeled-records.jsonl --engine jev
python -m scripts.evaluate_reconciliation --dataset data/labeled-records.jsonl --engine llm --llm-model deepseek/deepseek-v4-flash
```

The last two commands make paid requests. Compare false merges, missed matches (including review), review rates, API failures, p50/p95 and actual reported cost. The conventional LLM baseline supplies hard labels without calibrated confidence; its adapter explicitly marks that limitation. Evaluation permits semantic acceptance only in its isolated policy argument and does not enable production matching. This measures pair classification; downstream journey accuracy requires separate recorded journeys and operator outcomes.

## Classifier and phone repair verification

The old closed vocabulary removed all place context, including supported locations. The corrected state retains only configured public terminal identifiers and route structure. Known Malayalam route forms parse deterministically, while unsupported places still require coverage clarification. A clear tracking paraphrase such as “Could you locate my bus right now?” now routes through rules even during a Jev outage.

The running server reproduced a failed cold classification under the original two-second deadline. The bounded deadline is now four seconds; it includes connection setup and concurrency waiting rather than allowing unbounded retries. The real endpoint also passed six labelled synthetic intent cases after the semantic-state repair: **6/6**, **466–1,049ms**, total reported cost **USD 0.000127932**. These are small synthetic compatibility checks, not a production accuracy benchmark.

Final mobility regression run: **224 tests passed in 20.254s**. Android: **26 unit tests passed**, debug build succeeded, and `builds/sahara-passenger-phone-debug.apk` was installed on the connected phone with its saved settings retained. KSRTC collection through the restarted server returned **17 public-webpage services and five planned journeys** for Kozhikode–Bengaluru on 12 October 2026. The unrelated visa enrichment was removed from commute chat after a regression showed that the substring `us` in `bus` triggered extra external requests.

The final running server correctly routed three previously problematic tracking/connection phrases. The semantic vehicle-approach check used a real Jev call in **1,328ms** with no failure; clear tracking and connection phrases returned selected-journey guidance in about **20ms** without paid classification. Chat navigation accepts confidence and selected-choice probability of at least 0.90; independent transport matching retains its stricter thresholds and review policy. Below-threshold judgments continue to normal extraction.

A full live chat request, `Kozhikode to Bengaluru tomorrow only buses`, returned **10 initial journey options in 7.09s**. Additional source collection was still running at that first result; this is not background-completion latency. Known bus fares were labelled separately from incomplete total fares because access/egress costs were unverified. No booking was made.

OSM road guidance support is present, but the regional extract download failed on this connection; no actual road graph was enabled. Missing service geometry remains unavailable instead of becoming a fabricated polyline. See `PHONE_TEST_2026-10-11.md` for the connection, test steps and dataset preparation.
